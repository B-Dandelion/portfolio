운영 중인 데이터를
이관하고 검증한 과정

운영 중인 Firestore 데이터를 PostgreSQL로 이전하며 스키마를 재설계하고, 식별자·수강권·시간대·구버전 앱의 변경까지 검증했던 과정을 정리했습니다.

주제데이터 모델 · 서비스 운영프로젝트포레스트링전체 글Velog 원문 ↗

Velog에 게시한 개발 기록을 포트폴리오에 맞게 재구성했습니다. 핵심 설계 판단과 사례를 소개하며, 세부 과정은 원문에서 확인할 수 있습니다.

운영 데이터는 단순한 파일이 아니다

Firestore에서 PostgreSQL로 이전하기로 결정해도 기존 데이터를 새 테이블에 삽입하는 것만으로는 끝나지 않습니다. 수업 기록 하나가 누락되면 학원의 실제 일정이 달라질 수 있고, 수강권 상태가 바뀌면 수강생의 이용 권한도 달라집니다.

포레스트링은 이미 사용자들이 운영 중이던 서비스였습니다. 따라서 중요한 것은 데이터의 총량이 아니라 원본 데이터가 가진 의미와 관계를 새로운 구조에서도 보존하는 것이었습니다.

기존 구조를 분석하고 새 모델과 매핑하기

먼저 Firestore의 컬렉션·문서·하위 컬렉션과 필드를 다시 살펴보았습니다. 데이터가 무엇을 뜻하는지만이 아니라 어떤 기능에서 생성되고 수정되는지, 과거의 예외 규칙은 무엇인지까지 파악해야 했습니다.

새 구조에 기존 문서를 일대일로 대응시키는 데 집착하지 않았습니다. 정규 일정의 반복 규칙은 lesson_series, 실제 개별 수업은 lessons, 수강권은 lesson_rights, 선생님 배정 기간은 teacher_student_assignments 등 서로 다른 개념으로 분리했습니다.

외래 키를 정의하면 참조 대상 행이 존재해야 합니다. 그렇기 때문에 원본 필드가 어느 테이블로 이동하는지, 어떤 식별자로 연결되는지, 합쳐지거나 제외되는 값은 무엇인지 명확한 매핑이 필요했습니다.

AI로 변환 코드를 작성하더라도 설계의 기준은 개발자가 이해해야 합니다.

어떤 값이 정상이고 어떤 관계가 반드시 유지되어야 하는지 정의하지 못하면, 변환 스크립트가 오류 없이 실행되더라도 결과가 올바른지 판단하기 어렵습니다.

원본 데이터 추출과 백업

기존 데이터는 새로운 구조로 변환한 뒤에도 원본과 별도로 보존했습니다. Firebase Admin SDK 스크립트를 이용해 Firestore의 컬렉션과 하위 컬렉션을 재귀적으로 조회하고 JSON 형태로 추출했습니다.

이때 문서 ID, 하위 컬렉션, Timestamp 등의 타입 의미가 보존되는지 확인해야 합니다. 또한 Firestore 데이터를 추출한 것과 Firebase Authentication을 포함한 프로젝트 전체를 백업한 것은 서로 다른 일입니다. 실제 운영 중에는 추출 시점 이후에 발생한 변경을 어떻게 반영할지도 고려해야 합니다.

원본을 남겨 둔 이유는 '언젠가 쓸 수도 있기 때문'이라는 막연한 기대가 아니라, 변환 결과에서 누락이나 불일치가 발견되었을 때 어떤 값이었는지 다시 확인할 근거가 필요했기 때문입니다.

데이터를 옮기고 기능 단위로 검증하기

외래 키가 있는 테이블에서는 참조하는 대상 데이터가 먼저 준비되어야 합니다. 하지만 학생 테이블의 적재가 끝났다고 해서 수업 예약 기능까지 이관이 끝난 것은 아닙니다.

수업 예약이 정상 동작하려면 학생과 선생님, 정규 일정, 개별 수업, 수강권이 올바르게 연결되어야 합니다. 따라서 적재 순서는 데이터 의존성을 기준으로 계획하면서, 완료 여부와 검증 범위는 예약·취소·학생 등록처럼 실제 사용 기능을 기준으로 확인했습니다.

이처럼 기능별로 나누어 검증하는 작업과, 많은 행을 여러 묶음으로 삽입하는 데이터 배치 처리는 다른 개념입니다. 후자에서는 실패한 배치를 재실행할 때 중복 데이터가 생기지 않도록 만드는 것이 중요합니다.

기존 식별자를 보존하고 중복 삽입 막기

새로운 계정 식별자로 UUID를 사용하더라도 Firebase 계정과의 연결 정보는 필요했습니다. 그래서 PostgreSQL의 profiles 테이블에는 과거 식별자를 기록하는 legacy_id text unique 필드를 두었습니다.

실제로 전체 이관 이후 과거 수업 기록을 추가 복구할 때도 기존 Firebase 수업 ID를 바탕으로 기록의 출처를 추적하고, 동일한 기록이 있으면 중복 삽입을 건너뛰도록 만들었습니다. 복구 함수는 삽입·중복 건너뜀·기간 제외·실패를 구분해 결과를 반환하며, 오류가 발생하면 배치를 롤백하도록 하는 별도 형태도 마련했습니다.

이 과거 이력 복구 함수는 최초 전체 이관에 사용한 스크립트와 동일한 것은 아닙니다. 다만 재실행 가능성과 멱등성이 운영 데이터 복구에서 왜 중요한지를 잘 보여줍니다.

수량이 일치해도 정합성을 확인해야 한다

정규화 과정에서는 원본 문서 하나가 여러 테이블의 행으로 분리되거나 여러 기록이 하나로 통합될 수 있습니다. 따라서 원본과 대상의 행 수가 같다는 사실만으로 이관 성공을 판단할 수 없습니다.

식별자 매핑, 참조 무결성, 상태 일관성, 날짜 의미, 실제 예약·취소 동작을 함께 검증해야 합니다. 아래 가상 데이터에서 직접 정합성을 검사해 볼 수 있습니다.

INTERACTIVE / DATA VALIDATION

건수가 같아도 이관이 성공한 것은 아니다

두 테이블 모두 수업 기록은 2건입니다. 검증을 실행해 무엇이 잘못되었는지 확인해 보세요.

수량 검사만으로는 두 테이블 모두 2건이어서 문제가 드러나지 않습니다.

실제 운영 데이터가 아닌 교육용 가상 사례입니다. SQL 검사·외래 키·업무 규칙 검증의 필요성을 보여주기 위한 실습입니다.

이런 검증은 SQL과 스크립트로 반복 가능하게 만들어야 합니다. AI가 작성한 JOIN 조건이나 검증 쿼리 자체가 잘못될 수도 있으므로, 검사 기준과 결과를 직접 대조하는 과정이 필요합니다.

시각과 날짜의 의미를 보존하기

포레스트링은 한국 시간을 기준으로 운영됩니다. 실제 수업 시작 시각과 휴원일·퇴원일처럼 달력상의 날짜가 중요한 데이터는 서로 다르게 취급해야 합니다.

한국 시간 10월 2일 00시를 UTC로 표현하면 10월 1일 15시입니다. 이것은 정상적인 시간대 변환입니다. 오류는 UTC 날짜인 10월 1일을 한국 달력의 10월 2일 대신 업무 규칙에 적용하는 경우에 발생합니다.

-- timestamptz에서 한국 기준 날짜 추출
(v_starts AT TIME ZONE 'Asia/Seoul')::date

이관에서는 컬럼의 형식만 맞추는 것이 아니라, 원본 날짜와 시각이 의미하는 기준까지 보존해야 합니다.

구버전 앱과 새 데이터베이스가 공존하던 기간

모바일 앱에서는 새 버전을 배포하더라도 모든 사용자가 즉시 업데이트하지 않습니다. 예전 앱이 Firestore에 쓰고 새 앱이 Supabase에 쓰는 기간에는 데이터가 서로 다른 위치에 기록될 수 있습니다.

포레스트링에서는 Supabase 연결 앱을 배포해 업데이트를 권장한 뒤, 구버전에서 Firestore에 발생하는 새 쓰기를 탐지하고 변경된 기록을 추가 이관하는 방식으로 대응했습니다. 시간이 지나면서 구버전 사용도 줄었습니다.

이 과정은 작은 서비스에서 선택한 대응 방식이지 모든 서비스에 일반적으로 권장할 수 있는 전환 전략은 아닙니다. 동기화 지연·중복·충돌을 고려해야 하며, 더 엄격한 정합성이 필요한 시스템에서는 쓰기 중단 후 최종 이관이나 변경분 동기화, 복구 계획을 별도로 설계해야 합니다.

데이터 이관과 서비스 전환은 서로 다른 작업입니다.

새 DB에 데이터가 존재하는 것만으로는 충분하지 않습니다. 모든 앱 버전에서 발생하는 쓰기가 어떤 시스템에 기록되는지까지 관리해야 전환이 마무리됩니다.
