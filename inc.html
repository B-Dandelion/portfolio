INC 홈페이지:
자료를 찾고 관리하는 구조를 만들다

흩어진 발간물, 세미나, 워크숍과 보고서 자료를 한곳에서 조회하고 관리할 수 있는 권한 기반 웹사이트를 1인 개발했습니다.

역할웹 프론트엔드·서버 API·DB·배포 / 1인 개발기술Next.js, TypeScript, Supabase, R2운영Vercel

01. 조회와 관리가 함께 필요한 홈페이지

기관의 발간물·세미나·워크숍·보고서가 여러 경로와 형식으로 존재하면 이용자는 자료를 찾기 어렵고, 관리자는 공개 범위와 업로드 상태를 개별적으로 확인해야 합니다.

자료 유형에 맞는 게시판과 검색 흐름을 구성하고, 관리자가 콘텐츠를 직접 등록·수정·정리할 수 있는 홈페이지를 만들었습니다. 요구사항 정리 이후 웹 구조, UI, 서버 API, 데이터·권한 설계, 저장소 연동, 자료 이관과 배포를 1인 개발로 진행했습니다.

02. 방문자의 탐색과 관리자의 작업을 연결

공개 페이지
기관 소개, 공지와 행사, 자료 유형별 목록·상세와 검색 흐름을 제공합니다.
자료 조회
게시판별 분류·정렬과 공개 범위를 반영합니다. 서버 조회에서는 로그인 상태와 회원 승인 여부에 따라 접근 가능한 자료를 구분합니다.
관리자 도구
자료 등록·수정·삭제, 파일·YouTube URL 등록, 공지·행사·회원 관리를 지원합니다. 관리자 API는 작업 전에 권한을 확인합니다.

Next.js App Router와 TypeScript로 공개 페이지와 서버 API를 함께 구성했습니다. Supabase Auth는 인증을, PostgreSQL은 자료와 권한 관련 정보를, Cloudflare R2는 원본 파일 저장을 담당합니다.

공개 범위를 반영한 자료 조회 ↗관리자 요청 검증 ↗

03. 찾기 위한 정보와 읽을 파일을 분리

제목·게시판·게시일·공개 범위·파일 키는 관계형 데이터로 조회해야 하지만, 문서·이미지·영상의 원본은 객체 저장소에 적합했습니다. 검색·목록 조회와 파일 제공의 책임을 나누기 위해 PostgreSQL과 R2를 함께 사용했습니다.

자료의 공개 범위는 public / member / admin으로 구분합니다. 업로드 시 공개 자료와 비공개 자료의 버킷을 나누고, 서버에서 요청자의 인증·승인 상태와 자료의 범위를 확인합니다.

04. 파일만 저장되고 DB 등록이 실패한다면?

R2 업로드와 DB INSERT는 하나의 DB 트랜잭션으로 묶을 수 없습니다. 정상 흐름만 구현하면 메타데이터가 없는 파일이 저장소에 남을 수 있습니다.

  1. 요청 검증

    관리자 권한, 제목·게시판·공개 범위와 파일 입력을 확인합니다.

  2. 파일 업로드 → 메타데이터 등록

    R2에 원본을 저장하고, 파일 키와 함께 PostgreSQL에 자료를 등록합니다.

  3. DB 등록 실패 → 보상 삭제 요청

    이미 올린 R2 객체에 DeleteObject를 요청하고 실패 응답을 반환합니다.

이는 두 시스템을 원자적으로 묶은 처리가 아니라, 한쪽만 성공했을 때 정리를 시도하는 보상 처리입니다. 현재 구현은 삭제 요청 실패를 별도로 보고하지 않으므로, 남은 객체 탐지와 재시도는 후속 보완 과제입니다.

업로드와 DB 실패 시 보상 처리 ↗

05. 기존 자료도 새 구조 안으로

신규 업로드 화면만으로는 기존 자료를 옮길 수 없었습니다. 로컬 폴더의 파일을 순회하며 파일명과 경로에서 게시일·분류 정보를 정리하고, R2 업로드와 PostgreSQL 등록을 수행하는 스크립트를 작성했습니다.

이관 스크립트는 실제 쓰기를 수행하지 않는 DRY_RUN, 등록 배치 크기, 날짜 추출 검증 옵션을 제공합니다. 파일의 제목·날짜를 새 메타데이터와 연결하는 규칙을 코드로 남겨 수작업 업로드의 반복을 줄이는 방향으로 구성했습니다.

파일 순회·날짜 해석·이관 스크립트 ↗

06. 화면 바깥의 실패까지 설계하는 경험

Vercel에 배포한 홈페이지에서 공개 페이지와 관리자 기능을 함께 운영할 수 있도록 구성했습니다. 이번 프로젝트에서는 UI 개발 외에도 접근 범위, 저장소 간 상태 차이, 기존 데이터의 형식과 이관 흐름을 직접 다뤘습니다.

외부 서비스의 경계가 실패의 경계이기도 합니다.

기능을 연결하는 것과 실패 뒤의 상태를 설명할 수 있는 것은 다른 문제였습니다. DB와 파일 저장을 나눌 때는 정상 흐름뿐 아니라 보상 처리의 한계도 함께 살펴야 한다는 점을 배웠습니다.
