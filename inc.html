운영 중인 서비스를
측정하고 고치다

흩어진 발간물, 세미나, 워크숍과 보고서 자료를 한곳에서 조회하고 관리할 수 있는 권한 기반 웹사이트를 1인 개발했습니다. 공개 후에는 실제 이용 데이터와 측정값을 근거로 느린 원인과 잘못된 집계를 찾아 고쳤습니다.

자료 수는 2026.10.20 운영 DB 기준이며 삭제 처리한 자료는 제외했습니다. API·화면 수(44개)와 커밋 수는 2026.10.22 저장소 main 기준입니다. 공개 범위는 public / member / admin 3단계입니다.

01. 흩어진 자료를 한곳에

기관의 발간물·세미나·보고서가 서로 다른 경로와 형식으로 존재할 때, 이용자는 원하는 자료를 찾기 어렵고 관리자는 공개 범위와 업로드 상태를 일일이 확인해야 합니다.

자료 유형에 맞는 게시판과 검색 흐름을 만들고, 관리자가 직접 콘텐츠를 등록·수정·정리할 수 있는 환경을 구축했습니다.

02. 정보는 DB에, 파일은 저장소에

자료의 제목, 작성일, 게시판, 공개 범위는 PostgreSQL에서 관리하고 실제 문서·이미지·영상 파일은 Cloudflare R2에 저장했습니다. Next.js 서버 API에서 인증, 입력 검증, 공개 범위 판단과 업로드 흐름을 제어하도록 나누었습니다.

Next.js→Supabase / Metadata+Cloudflare R2 / Files

자료 정보와 객체 저장을 분리해 검색·목록 조회와 실제 파일 제공의 책임을 구분했습니다.

공개 범위를 public / member / admin으로 구분하고, 삭제 상태·검색어·카테고리·날짜 등을 조회 조건으로 반영했습니다.

526PDF104이미지24영상16문서9슬라이드

자료 삭제는 행을 지우지 않고 삭제 시각만 기록하는 방식으로 처리합니다. 목록과 검색에서는 빠지지만 기록은 남아, 지금까지 삭제한 37건도 언제 지웠는지 확인할 수 있습니다. 관리자 화면의 삭제에 "되돌리기"를 붙일 수 있었던 것도 이 구조 덕분입니다.

03. 실패하는 경우부터 설계

파일은 올라갔는데 DB 저장이 실패하면

서로 다른 저장소는 하나의 데이터베이스 트랜잭션으로 묶이지 않습니다. 파일 업로드만 성공하고 자료 메타데이터 저장이 실패하면 저장소에는 조회되지 않는 객체가 남을 수 있습니다.

처음에는 파일이 서버를 거쳐 R2로 갔는데, Vercel 함수는 요청 본문을 4.5MB까지만 받기 때문에 큰 PDF와 영상은 올릴 수 없었습니다. 그래서 브라우저가 서명된 주소(presigned URL)로 R2에 직접 올리고, 서버는 등록만 맡도록 흐름을 바꿨습니다.

브라우저 → R2 직접 업로드

서버는 파일 형식·크기·민감한 파일명을 검사한 뒤 업로드 주소만 발급합니다.

파일이 실제로 있는지 확인 후 DB 등록

클라이언트의 "업로드 완료"를 믿지 않고, 서버가 저장소에 객체가 있는지 직접 확인한 뒤 레코드를 만듭니다.

DB 저장 실패 시 업로드 객체 삭제

파일만 고립된 상태로 남지 않도록 보상 처리합니다.

개발자가 아닌 담당자를 위한 업로드

실제 사용자는 자료를 올리는 기관 담당자입니다. 여러 파일을 한 번에 끌어다 놓으면 3개씩 동시에 올라가고, 파일마다 실제 진행률이 보이며, 실패한 파일만 다시 시도할 수 있게 했습니다. 행사 편집 화면은 공개 페이지와 같은 배치로 만들어, 결과물을 보면서 포스터·사진·자료를 끌어다 놓고 순서를 바꾸도록 했습니다.

자료 목록의 수정은 화면에 먼저 반영하고(낙관적 업데이트), 서버 저장이 실패하면 이전 상태로 되돌린 뒤 알려줍니다. 브라우저 기본 prompt() 창 세 개로 하던 편집은 목록 안에서 바로 고치는 폼으로 바꿨고, 삭제는 확인 창과 되돌리기를 거치게 했습니다.

04. 측정으로 찾은 느린 원인 세 가지

공개 후 "페이지가 느리다"는 같은 증상 뒤에 서로 다른 원인이 세 개 있었습니다. 각각 응답 시간을 재고, 원인을 확인한 뒤에만 고쳤습니다.

증상측정으로 찾은 원인전후
홈 첫 응답요청은 서울 리전으로 들어오는데 함수는 미국 동부에서 실행되어, 서울 DB를 매 쿼리마다 태평양 건너 조회. 실행 리전을 서울로 고정하고 홈의 세 섹션을 병렬로 조회1.7–2.2초0.08–0.11초
모든 페이지가 매번 DB 조회루트 레이아웃이 언어 쿠키를 읽어 전 페이지가 동적 렌더링. 공개 조회 함수 13개를 캐시하고, 관리자가 수정한 테이블의 캐시만 태그로 즉시 만료수정은 바로 보이고 방문자는 캐시로 응답
Heartbeat 호 첫 열람150–200쪽 PDF 전체에서 글을 추출. 칼럼과 목차가 있는 앞 12쪽만 읽고, 추출 결과는 관리자 수정과 무관한 별도 캐시에 보관, 업로드 직후 미리 생성최대 7–8초0.1–0.2초

응답 시간은 운영 사이트에 직접 요청해 첫 바이트까지 걸린 시간(TTFB)입니다.

05. 브라우저·React 동작에서 생긴 버그

보이기만 해도 오르던 조회수

조회수 상위 12개가 모두 행사 사진이었습니다(최고 131회). 원인은 <img src>가 파일을 열 때 조회수를 올리는 주소를 그대로 쓰고 있던 것입니다. 브라우저는 이미지를 그리기 위해 그 주소를 요청하므로, 사람이 사진을 고르지 않아도 페이지가 열릴 때마다 조회와 다운로드가 기록되었습니다.

"화면에 표시하는 요청"과 "사용자가 연 요청"을 다른 주소로 나눴습니다. 표시용 주소는 집계를 하지 않고 이미지를 화면 크기에 맞게 줄여 CDN에 캐시하며, 조회는 사용자가 파일이나 간행물 페이지를 연 시점에만 기록하고, 간행물 페이지는 같은 브라우저의 30분 내 새로고침과 검색 로봇을 제외했습니다.

수 MB → 27KB행사 사진 평균 크기0회변경 후 표시만으로 오른 조회수

입력할 때마다 다시 그려지던 목록

1,390줄짜리 관리자 컴포넌트를 나누다가, 자료 행 컴포넌트가 부모 함수 안에 선언되어 있는 것을 발견했습니다. React는 렌더링마다 새로 만들어진 함수를 다른 컴포넌트로 보기 때문에, 입력창에 한 글자를 칠 때마다 등록된 자료 행이 전부 언마운트·마운트되고 있었습니다. 모듈 최상위로 옮겨 해결하고 컴포넌트는 896줄로 줄었습니다.

버튼 글자가 배경색에 묻히던 문제는 전역 CSS의 a { color: inherit }가 레이어 밖에 있어 Tailwind 유틸리티보다 우선하던 것이 원인이었습니다. !important로 덮지 않고 원인 규칙을 지웠습니다.

06. 기존 기능을 지키는 검증

운영 중인 서비스라 "기존 기능을 줄이지 않는다"가 기본 조건이었습니다. 그래서 변경마다 무엇으로 확인할지를 먼저 정했습니다.

  • 화면 공통화: 세미나·워크숍·보고회·공모전 5개 게시판을 하나의 컴포넌트 구조로 합친 뒤, 11개 행사 페이지 각각이 연결하는 파일 목록을 운영 사이트와 대조해 누락 0건과 유튜브 영상 11개 유지를 확인했습니다.
  • PDF 글 추출: 2023–2026년 호를 기준으로 파서를 검증하고, 예상과 다른 레이아웃은 원문 텍스트로 대체해 빈 페이지가 나오지 않게 했습니다.
  • 코드 품질: ESLint 오류 68개(any 67개)와 경고 22개를 0으로 만들고, push와 PR마다 lint·타입 검사·빌드를 돌리는 CI를 붙였습니다.
  • 접근성: 공개 페이지의 낮은 글자 대비를 WCAG AA 기준으로 올렸습니다.

07. 결과와 배운 점

웹 UI를 만드는 일 외에도 자료 저장 위치, 접근 권한, 업로드 실패, 기존 데이터 이관이라는 운영 영역을 직접 다뤘습니다. 공개 이후에는 PDF 안에만 있던 간행물 433호를 검색되는 웹페이지로 바꿔 사이트맵 주소를 21개에서 467개로 늘렸습니다.

가장 크게 배운 것은 고치기 전에 재는 습관입니다. 느린 페이지 세 곳은 원인이 모두 달랐고, 조회수 문제는 코드가 아니라 데이터의 이상한 분포에서 먼저 드러났습니다.
