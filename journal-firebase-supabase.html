Firebase에서 Supabase로,
운영 중인 예약 앱의
데이터베이스를 옮긴 이유

개발 편의성으로 시작한 Firestore에서 관계형 데이터의 무결성을 고민하게 됐습니다. 실제 예약 시스템을 운영하며 PostgreSQL을 선택한 기술적 이유를 정리했습니다.

주제데이터 모델 · 기술 선택 · 서비스 운영프로젝트포레스트링원문Velog

이 글은 Velog에 공개한 개발 기록과 작성 원고를 바탕으로 포트폴리오 웹사이트에 맞게 재구성한 버전입니다.

빠르게 출시하기 위한 선택

포레스트링은 바이올린 학원의 수업 예약·취소·일정 관리를 위한 Flutter 앱입니다. 첫 버전을 만들 당시에는 서버를 직접 구축하지 않아도 되고 Flutter와 연동하기 쉬운 Firebase가 적합했습니다. 중요한 것은 실제 사용자가 이용할 MVP를 완성하는 일이었기 때문입니다.

초기에는 학생 정보를 저장하고 수업을 생성해 화면에 표시하는 것으로 충분했습니다. 그러나 운영을 이어 가면서 수업, 수강권, 학기, 담당 선생님과 그 변경 이력이 하나의 규칙으로 연결되기 시작했습니다.

수업 취소가 단순한 상태 변경이 아니었던 이유

수강생이 수업을 취소하면 수업의 상태뿐 아니라 취소 가능한 횟수, 반환할 수강권, 수강권의 이월 여부, 담당 선생님과 과거 이력까지 확인해야 합니다. 이미 사용한 수강권을 다시 쓸 수 없도록 보장하는 일도 필요했습니다.

초기 구조에서는 isRescheduled, isActive 같은 Boolean 필드로 상태를 표현하다가 기능이 늘어나며 status를 추가했습니다. 문제는 필드 하나를 늘릴 때마다 그 값을 참조하는 예약·취소·보강·조회 코드를 모두 점검해야 했다는 점입니다. 수정하지 못한 경로가 남으면 같은 수업을 서로 다른 상태로 판단할 수도 있었습니다.

개선할 대상은 특정 필드가 아니라 데이터 관계를 관리하는 방식이었습니다.

서비스가 커질수록 데이터의 유효한 상태를 어디에서, 어떻게 보장할지 중요해졌습니다.

Firestore Standard와 PostgreSQL의 데이터 모델

Cloud Firestore Standard는 컬렉션과 문서를 중심으로 데이터를 저장합니다. 조회 패턴에 맞춰 정보를 한 문서에 모으거나 필요한 데이터를 중복 저장할 수 있습니다. 반면 PostgreSQL은 테이블을 관계로 연결하고 외래 키, 제약 조건, SQL JOIN으로 데이터를 다룰 수 있습니다.

Firestore에서도 복잡한 예약 시스템을 만들 수 있습니다. 다만 관계형 JOIN이나 외래 키 제약을 그대로 제공하지 않는 Firestore Standard에서는 관련 문서를 조회하고 검증하는 책임을 별도 로직에 두어야 합니다. 아래는 그 구조적 차이를 단순화한 예시입니다.

아래 질문을 선택하면 Firestore Standard와 PostgreSQL에서 데이터를 연결하는 흐름이 바뀝니다.

Firestore Standard문서 조회 → 응용 계층에서 조합
    PostgreSQL관계를 이용한 SQL 조회

    개념을 설명하는 가상 예시입니다. Firestore에서도 데이터 중복 저장, 인덱스, 서버 측 함수 등을 이용해 조회를 최적화할 수 있으며, 위 그림은 실제 요청 횟수나 성능 비교를 뜻하지 않습니다.

    중요한 것은 어느 모델이 무조건 빠르다는 뜻이 아닙니다. 자주 수행하는 조회와 변경, 반드시 유지해야 하는 관계가 무엇인지에 따라 설계와 유지보수 비용이 달라집니다.

    서버 함수만 도입하면 해결됐을까?

    Flutter에 분산된 비즈니스 로직을 중앙화하려면 반드시 Supabase로 옮겨야 하는 것은 아닙니다. Firebase에서도 HTTPS Callable Cloud Functions를 Flutter에서 호출하고, 함수 내부에서 Firestore Transaction을 실행할 수 있습니다. Transaction은 여러 문서의 원자적인 변경을 보장하며, Batched Writes 역시 여러 문서를 한 번에 원자적으로 쓸 수 있습니다.

    다만 Transaction은 필요한 읽기를 쓰기보다 먼저 수행해야 하고 재시도와 충돌 가능성을 고려해야 합니다. Batched Writes는 배치 내부에서 문서를 읽어 현재 상태에 따라 판단하지 못합니다. 무엇보다 Callable 함수로 비즈니스 로직을 이동하더라도 문서 간 관계를 검증하기 위한 모델링과 코드는 여전히 필요합니다.

    PostgreSQL에서는 DB 함수가 JOIN과 관계형 제약을 활용해 필요한 데이터를 검증한 후, 같은 트랜잭션에서 변경할 수 있습니다. Supabase는 이러한 함수를 Flutter에서 RPC로 호출할 수 있게 합니다. 실제 포레스트링에서도 수업 취소 요청을 cancel_lesson RPC로 처리하도록 역할을 분리했습니다.

    // Flutter에서 DB 함수 호출 (단순화 예시)
await supabase.rpc(
  'cancel_lesson',
  params: {
    'p_lesson_id': lessonId,
    'p_reason': reason,
  },
);

    Firestore 이벤트 기반 Cloud Functions는 원본 데이터 변경 이후 비동기로 실행되며 중복 전달 및 순서 문제를 고려해야 합니다. 반면 PostgreSQL의 일반적인 데이터 변경 트리거는 해당 변경과 동일한 트랜잭션에서 실행됩니다. 그렇다고 모든 처리를 트리거에 넣은 것은 아닙니다. 명시적인 업무 처리는 DB 함수, 데이터 변경에 필수적으로 수반되는 검증은 제약과 필요한 트리거로 구분했습니다.

    데이터 관계를 데이터베이스 자체에서 지키기

    학생에게 선생님을 배정할 때는 현재 담당자만 저장하는 것으로 충분하지 않았습니다. 배정 시작일과 종료일을 저장해 담당자가 변경되어도 과거 관계를 유지할 수 있도록 했습니다. PostgreSQL의 teacher_student_assignments 테이블에서는 학생의 배정 기간이 서로 겹치지 않도록 EXCLUDE 제약을 사용합니다.

    EXCLUDE USING gist (
  student_id WITH =,
  daterange(starts_on, ends_on + 1, '[)') WITH &&
)

    개념을 간결하게 보여주는 발췌입니다. 실제 스키마는 종료일이 없는 배정도 고려하며, 정확한 조건은 프로젝트 마이그레이션 코드에서 확인할 수 있습니다.

    이런 제약은 특정 Flutter 화면에서만 검사하는 조건과 다릅니다. 데이터를 변경하는 경로가 달라져도 데이터베이스가 최종적으로 관계를 검사합니다. 물론 수업 취소 기한처럼 업무 특화 규칙은 별도로 구현해야 합니다.

    비용과 운영을 함께 고려하다

    Firestore Standard는 문서 읽기·쓰기·삭제 및 인덱스 관련 작업, 저장 공간과 네트워크 사용량 등이 비용에 영향을 줍니다. Cloud Functions를 이용해도 함수 내부의 Firestore 작업량과 함수 실행 비용은 함께 고려해야 합니다. 복잡한 관계를 조회하기 위해 여러 문서를 반복 조회하는 구조를 장기적으로 확장하는 것이 부담스러웠습니다.

    실제로 Firebase 비용이 폭증한 적은 없습니다. 이는 발생한 비용 사고가 아니라 향후 운영 구조에 대한 우려였습니다. Supabase도 DB 컴퓨트 리소스, 스토리지와 네트워크 등에 비용이 발생하므로 무조건 더 저렴하다고 볼 수 없습니다.

    또한 Firebase는 하나의 기술만을 뜻하지 않습니다. 현재는 PostgreSQL 기반의 Firebase SQL Connect도 제공되며, Firestore Enterprise의 기능 역시 Standard와 다릅니다. 이 글의 선택은 당시 사용하던 Firestore Standard 구조와 포레스트링 요구사항을 기준으로 한 판단입니다.

    이관 후 달라진 책임의 경계

    이전에는 Flutter에서 여러 문서를 조회하고 규칙을 계산한 뒤 변경 사항을 쓰는 흐름이 많았습니다. 새로운 구조에서는 화면과 사용자 상호작용은 Flutter가 맡고, 데이터 정합성이 중요한 변경은 PostgreSQL의 함수·제약·트랜잭션에 더 많이 맡겼습니다.

    덕분에 서버에 정의한 업무 규칙을 변경할 때, 기존 RPC 계약이 유지된다면 앱을 다시 배포하지 않고도 수정 사항을 적용할 수 있게 됐습니다. 물론 함수의 호출 형식이 바뀌거나 화면 변경이 필요한 경우에는 하위 호환성과 앱 업데이트가 여전히 필요합니다.

    결국 이전의 핵심은 Firebase에서 불가능했던 기능을 얻는 일이 아니었습니다. 서비스의 관계형 데이터와 변경 규칙을 보다 명시적이고 일관된 구조에서 관리하는 것이었습니다.
