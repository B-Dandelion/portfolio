CASE STUDY 01 / MOBILE SERVICE

포레스트링.

수업을 예약하는 앱에서,
학원의 운영 규칙을 담는 서비스로.

실제 바이올린 학원의 선생님·관리자·수강생이 사용하는 Flutter 앱입니다. 약 2년간 혼자 개발하고 운영하며, 예약 기능을 넘어 수업 데이터와 권한의 일관성을 다듬었습니다.

01 / CONTEXT

같은 시간표로 설명되지 않는 수업

바이올린 학원에는 매주 고정 시간에 오는 수강생도 있고, 일정에 따라 빈 시간에 예약해야 하는 수강생도 있었습니다. 취소·보강과 휴원 기간까지 반영하려면 단순한 달력 이상의 운영 규칙이 필요했습니다.

학원에서 수업 일정을 모바일로 관리할 수 있는 앱을 요청받았습니다. iOS와 Android를 함께 지원하기 위해 Flutter를 선택하고, 운영자와 수강생의 사용 목적에 맞춰 두 앱으로 나누었습니다. 요구사항 정리부터 데이터 구조, 구현, 스토어 배포, 운영 중 오류 대응까지 직접 맡았습니다.

02 / PRODUCT & ROLE

화면은 역할에 맞게,
수업 데이터는 하나로

운영 앱은 선생님·지점장·전체 관리자의 범위를 구분하고, 수강생 앱은 본인 일정과 취소·보강 흐름에 집중합니다. 두 앱은 동일한 Supabase 스키마를 사용합니다.

선생님
본인 수업의 월간·주간 일정과 담당 수업 정보를 확인합니다.
지점장·전체 관리자
권한 범위 안에서 수강생·선생님·지점을 관리하고, 수업 변경·취소·추가, 학기·휴원 설정과 다음 학기 준비를 처리합니다.
수강생
본인 일정과 상세를 조회하고, 취소 가능 조건을 확인해 수업을 취소합니다. 반환된 수업권으로 가능한 시간을 조회해 보강을 예약하고 학기별 이력을 확인합니다.

수강생 일정·예약 Repository ↗

03 / ARCHITECTURE

Firebase에서 PostgreSQL로 옮긴 이유

초기 Firestore 구조는 MVP를 빠르게 만드는 데 유용했습니다. 운영이 이어지면서 수강생·수업·선생님·수업권 관계를 함께 조회하고, 여러 상태 변경을 추적하는 일이 중요해졌습니다. 중첩 문서와 앱 곳곳에 분산된 변경 로직은 문제 원인을 확인하기 어렵게 만들었습니다.

초기 구조

Firebase 중심의 문서 저장과 클라이언트 처리. 기능을 먼저 구현하는 데 집중했습니다.

이전 후의 구조

관계·제약조건을 PostgreSQL에 정의하고, 중요한 상태 변경은 Repository를 거쳐 RPC와 서버 검증으로 처리합니다.

SDK만 교체하지 않고 지점·역할·학기·수업권을 관계형 모델로 정리했습니다. 스키마, RLS, RPC와 일정 자동화 변경은 Supabase migration 파일로 관리합니다. 화면은 입력과 상태 표현을 담당하고, 바뀌면 안 되는 규칙의 검증 경계를 서버 쪽에 두었습니다.

이전 과정과 설계 요약 ↗스키마·운영 규칙 변경 이력 ↗

04 / DATA INTEGRITY

취소와 보강은 하나의 수업권 생명주기

취소를 새 일정 생성과 별개로 다루면 같은 권리를 여러 번 사용하거나, 취소와 보강 기록의 연결이 끊길 수 있습니다. 수업권을 중심에 두고 예약·취소·재예약을 상태 변화로 연결했습니다.

동시에 같은 수업권으로 예약한다면?

예약 RPC는 수업권을 FOR UPDATE로 잠그고 소유자·지점·사용 가능 상태를 확인합니다. 클라이언트가 수업권과 시작 시각을 전달하면 서버가 담당 선생님, 수업 길이와 예약 가능 여부를 판정합니다. 화면의 버튼 비활성화 외에도 DB 트랜잭션 안에서 같은 권리의 동시 사용을 제어한 것입니다.

취소 횟수와 기록도 함께 관리

취소 RPC는 수업과 수업권을 확인한 뒤 기존 수업권을 반환하고 취소 이력을 남깁니다. 같은 권리에 대해 취소 한도를 중복 집계하지 않도록 부분 유일 인덱스도 정의했습니다. 수업 일정만 바꾸는 대신 그 변경이 다른 운영 데이터에 미치는 영향을 함께 다뤘습니다.

수업권 예약·잠금 구현 ↗취소·반환·집계 구현 ↗

05 / AUTHORIZATION

메뉴를 숨기는 것에서 끝내지 않기

선생님은 본인 수업, 지점장은 담당 지점, 전체 관리자는 전체 운영 범위, 수강생은 본인 데이터에 접근해야 합니다. 역할별 화면 분기 외에 RLS와 서버 로직에서도 접근 범위를 검증하도록 구성했습니다.

예를 들어 예약 요청은 로그인 여부뿐 아니라 수업권의 소유자와 지점을 확인합니다. 선생님과 수강생을 연결할 때도 지점이 일치하는지 검증합니다. 클라이언트가 보낸 식별자를 그대로 신뢰하지 않고, DB에 저장된 역할과 관계를 기준으로 판단합니다.

역할별 RLS 정책 ↗지점 관계 검증 ↗

06 / OPERATION & LEARNING

출시 이후에 배운 서비스 개발

날짜 오류는 운영 규칙을 다시 보는 계기

휴원 기간과 정규 수업 생성 시점이 겹치면서 일정이 누락되거나 잘못 생성되는 오류를 겪었습니다. DB의 UTC 시각을 읽어 KST 날짜로 비교하는 기준을 점검했고, 날짜·일정 규칙이 클라이언트 여러 곳에 흩어져 있다는 구조적 문제까지 살피게 되었습니다.

“수정하기 편하게”라는 요청의 배경

고정된 시간표가 맞지 않는 수강생에게 취소와 보강을 반복하게 하는 것은 수정 화면만 개선해서 해결할 수 없었습니다. 고정 수업이 없어도 수업권으로 원하는 시간에 예약할 수 있도록 모델을 확장했습니다.

운영이 바꾼 개발 기준

앱이 실행되는가에서 한 걸음 더 나아가, 여러 역할과 화면이 같은 규칙을 지키는가를 살피게 됐습니다. 요구사항, 데이터 설계와 유지 보수를 하나의 과정으로 경험했습니다.

앱은 실제 학원에서 약 2년간 운영·유지 보수했습니다. 구체적인 운영 오류와 판단 과정은 별도의 회고에 담았습니다.
